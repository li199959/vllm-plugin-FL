# whisper-large-v3 PPU 适配报告（2026-11-10）

- 模型：`/mnt/cpfs/xiangbin/whisper-large-v3`（WhisperForConditionalGeneration，fp16）
- 环境：T-Head PPU 单卡（TP1），vLLM 0.24.0，`/v1/audio/transcriptions` 接口
- 插件：`vllm_plugin_fl-0.3.0rc1+ppu20261110-py3-none-any.whl`，常规 wheel 安装，不使用 PYTHONPATH，也不是 editable 模式

## 结论

| 项目 | 基线（仅 attention 走 FL） | 适配后（FlagGems 全开） | 目标 |
|---|---|---|---|
| WER（LibriSpeech test-clean，2620 条） | 1.929% | 1.933% | 与基线一致（官方约 2.0%） |
| 吞吐 RTFx，c64，3 轮交替 | 168.8 / 170.7 / 172.0 | 163.8 / 160.4 / 162.1 | 均值 95.1% |
| FlagGems 覆盖率（combined） | — | **84.21%**（32/38） | ≥80% |

- 基线是同一个插件，设置 `VLLM_FL_FLAGOS_WHITELIST=attention_backend`，其余算子走 aten/cuBLAS。这台机器装不了纯 vLLM。
- 吞吐取基线与适配交替测试的结果。基线自身轮间波动约 3%，单轮比值在 94.0%–97.0% 之间。
- 覆盖率中未覆盖的项都是 cuBLAS GEMM（aten.mm/addmm 和对应 kernel），原因是 GEMM 黑名单（见第 4 节）。

## 1. 启动命令

```bash
pip install --no-deps --force-reinstall vllm_plugin_fl-0.3.0rc1+ppu20261110-py3-none-any.whl   # 只需一次

export CUDA_VISIBLE_DEVICES=0
export VLLM_FL_FLAGOS_BLACKLIST_APPEND=broadcast_to,mm,mm_out,addmm,addmm_out,linear,empty
export VLLM_FL_WHISPER_COMPILE_ENCODER=1
export VLLM_FL_WHISPER_ENCODER_GRAPH_MAX=8
export VLLM_FL_WHISPER_COMPILE_PREFILL=1
export VLLM_FL_WHISPER_CROSS_SLOTS=1
vllm serve /path/to/whisper-large-v3 --served-model-name whisper-large-v3 --port 18365 \
  --gpu-memory-utilization 0.9 --no-enable-prefix-caching
```

基线启动：同一条 `vllm serve` 命令，只设置 `VLLM_FL_FLAGOS_WHITELIST=attention_backend`，不设置上面的变量。

| 环境变量 | 作用 |
|---|---|
| `BLACKLIST_APPEND=broadcast_to,...` | `broadcast_to` 在 CUDA graph 录制时做 H2D 拷贝，会直接报错。GEMM 和 linear 走 cuBLAS，因为 Gems GEMM 对每个新的 M 都要 autotune。`empty` 每次调用约 60 µs CPU。 |
| `WHISPER_COMPILE_ENCODER=1` | encoder 的 32 层用 torch.compile 编译成一张图（inductor 生成融合 Triton kernel）。vLLM 原版 encoder 完全不编译。 |
| `WHISPER_ENCODER_GRAPH_MAX=8` | ≤8 条音频的 encoder batch 走 CUDA graph 回放（按 batch 大小首次使用时录制），省掉每次约 33 ms 的 Python launch 开销。 |
| `WHISPER_COMPILE_PREFILL=1` | 有新请求的 step，先在 eager 下写好 cross-attention K/V，再走编译好的 decoder 图。vLLM 原版这类 step 整个 decoder 都跑 eager。 |
| `WHISPER_CROSS_SLOTS=1` | cross-attention slot mapping 改成每个 step 一次 gather。原来每个新请求要做 6 个小算子，每个约 150–750 µs CPU。 |

## 2. 精度测试命令

```bash
python3 tools/ppu/whisper/bench_asr.py --port 18365 \
  --data /path/to/LibriSpeech/test-clean --concurrency 64 --warmup 128 --out result.json
```

## 4. 覆盖率

- 方法：vllm-gpu-coverage skill（scan_trace + provenance + coverage）。
- 测试负载：最终配置，两轮预热后 profile 一轮 256 条请求，关闭 prefix cache。
- 结果目录：`profiles/whisper_final_cov_20261110/gpu_coverage`。

| | 覆盖 | 占比 |
|---|---|---|
| ATen | 16/18 | 88.89% |
| kernel | 16/20 | 80.00% |
| combined | 32/38 | **84.21%** |

- 未覆盖的 6 项是 `aten.mm`、`aten.addmm`、3 个 cuBLAS gemm tile 和 1 个 `gemvt_op`，都来自 GEMM 黑名单。
- 不加 encoder CUDA graph（v7）时 combined 是 91.43%。encoder graph 里的 cuBLAS kernel 无法映射回 ATen，所以多出几个未覆盖的 kernel 项。

## 5. 发现并修复的问题

1. **FlagGems conv1d 不支持非 batch 输入**：Whisper encoder 传入的是 `[128, 3000]`，Gems 把它当成 N=128、C=3000，profile run 阶段 assert 失败。
   - 修法：在 `patches/flaggems_contiguous.py` 里加一层守卫，补上 batch 维再去掉。
2. **FlagGems 调优缓存每次查询都反射整个 sqlite**：`SQLPersistantModel.build_sql_model_by_db` 用 `automap_base().prepare(engine)` 反射库里全部约 1500 张表，每次约 4 s，而且查不到的结果不缓存。
   - 现象：服务时 EngineCore CPU 100% 卡在 sqlalchemy，GPU 利用率 0%，启动要 450 s。
   - 修法：新增 `patches/flaggems_libcache.py`，先 `has_table`（0.2 ms），再只反射目标表（8 ms）。启动降到 70–80 s。这个修复对所有模型都生效。
3. **vLLM 编码器-解码器 step 全部走 eager**：Gems eager 算子每个 CPU 开销 150–550 µs（aten 约 30 µs），导致 GPU 利用率只有 42%。用第 1 节的编译开关解决。
   - encoder attention 改用自定义算子 `fl_whisper::encoder_sdpa`。原因是 vLLM 自带的 `torch_sdpa_wrapper` 的 fake 实现在 dynamo 下签名不匹配，而图一旦断开，dynamo 会把 Gems 的 Triton launch 内联进去，inductor 编译时报 `NameError: ext`。
4. `VLLM_FL_WHISPER_STABLE`（shape-stable index/copy_）在这个模型上没有收益，所以没有开启。

## 7. 注意事项

- encoder CUDA graph 是首次遇到某个 batch 大小时才录制的，所以刚启动时会慢一点。最多录 8 个 graph（1–8 条音频），共用一个内存池。这部分显存不计入 vLLM 启动时的显存 profile，在 `gpu-memory-utilization 0.9` 下全量测试没有出现 OOM。
- `COMPILE_PREFILL` 依赖 vLLM 0.24 的 `CrossAttentionImpl` / `do_kv_cache_update` 接口。升级 vLLM 后需要重新验证。
