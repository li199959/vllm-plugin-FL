bge-m3 性能、覆盖率与精度测试报告（2026-10-21）
==============================================

结论
----

| 项目 | 目标 | 结果 | 结论 |
|---|---|---|---|
| EvalScope 1024 输入，64 并发 256 请求 | ≥ 参考的 95% | 83.5 vs 86.3 req/s（96.8%） | 达标，余量 1.8% |
| EvalScope 4096 输入 | ≥ 参考的 95% | 10.32 vs 10.54 req/s（98.0%） | 达标 |
| EvalScope 8096 输入 | ≥ 参考的 95% | 3.29 vs 3.32 req/s（99.1%） | 达标 |
| 合计覆盖率 | ≥80% | 15/17（88.24%） | 达标 |
| embedding 精度 | 与 fp32 一致 | 42 条文本余弦最低 0.99980，均值 0.99999；检索排序一致 | 达标 |

- 参考配置：同一插件，只有 attention 走 Gems，其余是 torch/Inductor/cuBLAS。没有插件的纯 vLLM 在本机起不来（thead attention 在 vLLM 0.24 上 import 失败），所以没有更“原生”的基线。
- 启动后第一次跑 1024 时，v7 只有 40 req/s（p99 4.1 s）：Gems 首次见到这批形状，现场生成了 3 个 kernel（copy、add、int32 index）。第二轮起稳定，生成结果缓存在 `~/.flaggems/code_cache`，跨进程复用。上表是第 2–5 轮的稳态值。正式压测前建议先打一轮相同长度的预热。

1. 配置与命令
-------------

**最终配置（v7）**：代码在 `vllm_fl/optimizations/ppu/bge_m3/`、`../common/shape_stable.py` 和 `vllm_fl/worker/worker.py`（pooling 输出类型修复），通过 PYTHONPATH 加载本工作区，系统安装的插件未改动。

```bash
cd /mnt/cpfs/xiangbin/codex/minimax-m3-coverage-80
export PYTHONPATH=$PWD
export VLLM_DISABLE_COMPILE_CACHE=1     # vLLM 编译缓存的 key 不含 VLLM_FL_*，不关会复用旧图
# broadcast_to：Gems 版在 CUDA graph 捕获时做 H2D 拷贝，启动即崩
# mm/addmm/linear：大 batch GEMM 回 cuBLAS；empty：Gems 版每次约 60 µs CPU
export VLLM_FL_FLAGOS_BLACKLIST_APPEND=broadcast_to,mm,mm_out,addmm,addmm_out,linear,empty
export VLLM_FL_BGEM3_STABLE=1           # 运行期尺寸的 index / copy_，消除每个 batch 的重新生成
export VLLM_FL_BGEM3_DENSE=hybrid       # 接管 linear：≤512 token 的 batch 走 Gems linear_kernel
export VLLM_FL_BGEM3_GEMS_LINEARS=
export VLLM_FL_BGEM3_GEMS_SMALL_M=512
CUDA_VISIBLE_DEVICES=2 vllm serve /mnt/cpfs/xiangbin/codex/bge-m3 \
  --served-model-name BAAI/bge-m3 --runner pooling --port 8000 \
  --max-model-len 8192 --gpu-memory-utilization 0.9 \
  --compilation-config '{"max_cudagraph_capture_size":4096}'
```

脚本版：`NAME=BAAI/bge-m3 EXTRA_ARGS='--compilation-config {"max_cudagraph_capture_size":4096}' tools/ppu/bge_m3/serve_bge_m3.sh <run_dir> <gpu> <port> worktree`（环境变量同上）。

**参考配置**：`VLLM_FL_FLAGOS_WHITELIST=attention_backend`，其余参数相同（包括 `max_cudagraph_capture_size`）。

**压测**：你给的三条 EvalScope 命令（`random_embedding`，64 并发，256 请求，warmup 10），`--tokenizer-path` 指向本地模型目录。EvalScope 1.12.0 在 `profiles/qwen27b_eval_gpqa_erqa_20261006/evalenv`。

```bash
tools/ppu/bge_m3/evalscope_perf_bge_m3.sh <out_dir> <port> ["1024 4096 8096"]
```

v7（GPU 2，端口 8000）和参考（GPU 3，端口 8001）交替顺序跑，同一时段不并发压测。开跑前用 `ss -ltn` 确认端口只有一个监听者（vLLM 允许两个服务绑同一端口，曾因此混测）。

2. 性能结果
-----------

| 输入长度 | 轮次 | v7 req/s | 参考 req/s | v7 平均/P99 延迟 | 参考平均/P99 延迟 |
|---|---|---:|---:|---|---|
| 1024 | 1 | 40.01（冷启动） | 85.85 | 1.376 / 4.13 s | 0.643 / 0.85 s |
| 1024 | 2 | 82.63 | 86.35 | 0.668 / 0.89 s | 0.641 / 0.81 s |
| 1024 | 3 | 83.59 | 86.22 | 0.661 s | 0.640 s |
| 1024 | 4 | 83.75 | 86.25 | 0.653 s | 0.642 s |
| 1024 | 5 | 83.95 | 86.30 | 0.660 s | 0.642 s |
| 4096 | 1 | 10.32 | 10.53 | 5.388 / 5.95 s | 5.290 / 5.83 s |
| 4096 | 2 | 10.32 | 10.54 | 5.393 / 5.95 s | 5.277 / 5.82 s |
| 8096 | 1 | 3.29 | 3.32 | 17.03 / 18.70 s | 16.88 / 18.52 s |
| 8096 | 2 | 3.29 | 3.32 | 17.01 / 18.67 s | 16.87 / 18.51 s |

- 全部 256/256 成功。平均输入 1026 / 4098 / 8098 token（含 CLS/EOS）。
- 输入吞吐（req/s × 平均 token）：1024 约 85.7k vs 88.5k tok/s，4096 约 42.3k vs 43.2k，8096 约 26.6k vs 26.9k。EvalScope 表里的 `Inp.TPS` 是单请求的 token/延迟，不是总吞吐。
- 越短差距越大：长输入时 GPU 时间以 cuBLAS GEMM 和 attention 为主，两边相同；短输入时每个 step 更短，graph 外 eager 执行的小 Gems 算子（pooler 的 index/norm/div、输入准备）的 CPU 分发开销占比变大。

4. 覆盖率
---------

vllm-gpu-coverage skill 口径，profile 轮为 512 输入、64 并发、1024 请求（两轮预热 + 一轮 profile），`verification.json` 的 `checks_passed=true`。报告：`profiles/bge_m3_v7_cov_2014/gpu_coverage/`。

| | 覆盖 | 合计 |
|---|---:|---:|
| GPU 关联 ATen | 10 | 11 |
| 独立 GPU kernel | 5 | 6 |
| **合计** | **15** | **17（88.24%）** |

未覆盖：`aten.addmm`（大 batch GEMM 的 cuBLAS kernel 归在这里，约占 GPU 时间 57%）和一个 cuBLAS gemm tile。覆盖的 ATen 为 Gems 的 index/copy_/add/sub/fill_/zeros/div/linalg_vector_norm/clamp_min/_to_copy；覆盖的独立 kernel 为 Gems `linear_kernel`（小 batch 投影）、vLLM Triton attention（`_fwd_kernel`）和 Inductor 融合 kernel（embedding、LayerNorm、GELU）。

5. 精度
-------

**官方 dense 检查**：vLLM 官方 `tests/entrypoints/pooling/embed/test_bge_m3.py::test_bge_m3_api_server_embedding` 的断言（BAAI/bge-m3 模型卡给出的 2×2 相似度矩阵 `[[0.6259, 0.3474], [0.3309, 0.6734]]`，`torch.allclose(..., rtol=0.01)`），用 `tools/ppu/bge_m3/check_official_bge_m3.py` 对运行中的服务执行。

6. 原始配置的问题
-----------------

1. Gems `broadcast_to` 在 CUDA graph 捕获期间做 pinned H2D 拷贝，XLM-R 带 bias 的 linear 经 addmm 触发，启动即崩。
2. 插件 `worker.py` 未放行 pooling 模型返回的 `AsyncModelRunnerOutput`，第一个请求就让 engine 退出。
3. CLS pooler 的 `aten.index` 走 Gems，token 数写进生成的 kernel，几乎每个 batch 都重新生成并 autotune，p99 最高 14 s。
4. Gems mm/addmm 在 M=8192 时比 cuBLAS 慢 1.2–1.6 倍，占 GPU 时间 77%，全走 Gems 只有参考的 64%。
5. Gems `empty` 每次约 60 µs CPU，低并发时很明显。

各版本的演进与数据见 `README.md`。
