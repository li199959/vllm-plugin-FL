1. 配置与命令
-------------

**最终配置（v11）**：代码在 `vllm_fl/optimizations/ppu/qwen3_vl_moe/` 和 `../common/shape_stable.py`，通过 PYTHONPATH 加载本工作区，系统安装的插件未改动。

```bash
cd /mnt/cpfs/xiangbin/codex/minimax-m3-coverage-80
export PYTHONPATH=$PWD
export VLLM_DISABLE_COMPILE_CACHE=1      # vLLM 编译缓存的 key 不含 VLLM_FL_*，不关会复用旧图
export VLLM_USE_FLASHINFER_SAMPLER=0     # top-k/top-p 走 vLLM Triton，采样参数不变
export VLLM_FL_FLAGOS_BLACKLIST=mm,mm_out,addmm,addmm_out,linear,empty
export VLLM_FL_QWEN3VL_STABLE=1          # 运行期尺寸的 index / moe_align / copy_，消除重编译
export VLLM_FL_QWEN3VL_ATTN=fa3          # prefill 与 decode 都走 PPU FA3
export VLLM_FL_QWEN3VL_MOE=hybrid        # M=8192 走 DeepGEMM，其余走调过 tile 的 Gems
export VLLM_FL_QWEN3VL_DENSE=tuned       # decode 的 qkv / o_proj / router 走按 M 选 tile 的 Gems
vllm serve /mnt/cpfs/xiangbin/Qwen3-VL-30B-A3B-Instruct/ \
  --served-model-name qwen3-vl -tp 2 --port 8000 \
  --max-model-len 8192 --gpu-memory-utilization 0.9 --max-num-seqs 128 \
  --no-enable-prefix-caching             # 16k 场景: --max-model-len 20480
```

- 启动参数与用户命令一致，只多了 `--no-enable-prefix-caching`。
- 16k 输入超过 8192，这个场景改用 `--max-model-len 20480`。
- 原配置（native）：用户原命令，不设任何 `VLLM_FL_*`，同样关闭 prefix cache。
- 各开关的依据见 `README.md`。

**压测命令**（`tools/ppu/qwen3_vl_moe/bench_qwen3_vl.sh`，三个场景只有 `--random-input-len` 不同）：

```bash
vllm bench serve --backend vllm --model qwen3-vl \
  --tokenizer /mnt/cpfs/xiangbin/Qwen3-VL-30B-A3B-Instruct/ \
  --endpoint /v1/completions --host 127.0.0.1 --port <port> \
  --dataset-name random --random-input-len {1024|4096|16384} --random-output-len 1024 \
  --ignore-eos --max-concurrency 64 --num-prompts 128
```

- 共 128 个请求，并发 64。
- 第 0 轮是预热轮（Triton 编译、graph capture 都发生在这一轮），不计入结果。表中只列之后的稳态轮。
- 服务端关闭了 prefix cache。bench 每轮发的 prompt 相同，不关的话第 2 轮起 TTFT 会降到参考值的约十分之一，结果无效。

测量条件：

- 运行目录：`profiles/q_v11_{1k,4k,16k}_20261019`，原配置在 `profiles/q_np_native_4k_20261019`。
- GPU 分配：1k 用 GPU 14/15，4k 用 10/11，16k 用 12/13，以各目录 `serve.json` 为准。4k 和 16k 是两个服务同时压测的。
- 本机 GPU 0/1、4/5、8/9、12/13 是 NV2 卡对，其余是 NV1 卡对。16k 在 NV1 卡对上约慢 4%，所以 16k 的验收数据取 NV2 卡对。
- 关闭 prefix cache 后，原配置 4k 只有 793 tok/s，每轮有 2705 次超过 1 s 的 ITL 停顿。原因是 Gems pointwise 把 stride 当作 constexpr，M-RoPE 的切片 copy 会对每个 token 数都重编译一次。v11 的 `STABLE=1` 修复了这个问题。
- 原配置的 1k 和 16k 没有在同样条件下测，表中没有对照。

4. 算子覆盖率
-------------

- 统计口径：vllm-gpu-coverage skill，统计 GPU 关联的 ATen 和独立 GPU kernel。分子是 Gems 实现和有证据的 Triton kernel。
- 采集方式：4k/1k，64 并发，128 请求，预热后抓一轮 profile。
- 目录：`profiles/q_v11_cov_20261020/gpu_coverage`。

| 范围 | 已覆盖/总数 | 比例 |
|---|---:|---:|
| GPU 关联 ATen | 23/24 | 95.83% |
| 独立 GPU kernel | 30/41 | 73.17% |
| **合计** | **53/65** | **81.54%** |

- verification 通过。80 个原始 GPU kernel 符号都能通过映射表追溯。
- 未覆盖的 12 项：

| 未覆盖项 | 数量 | 原因 |
|---|---:|---|
| `aten.mm` | 1 | lm_head 等走 cuBLAS。改回 Gems 后覆盖率是 83.08%，但 4k/16k 会慢 2–3% |
| DeepGEMM grouped GEMM | 2 | 恰好 8192 token 的 prefill chunk 使用，比 Gems 快 1.84x |
| DeepGEMM `computeBlockInfoKernel` | 1 | DeepGEMM 的 permute |
| FA3 kernel | 5 | 3 个 forward、1 个 combine、`prepare_varlen`；prefill 比 Triton 快 3.4–4.2x |
| pccl 通信 | 3 | |

- 原配置的覆盖率是 39/44（88.64%），但它的 4k 吞吐只有 793 tok/s。按"覆盖率达到 80% 即可，余量用来换性能"的要求，v11 把部分覆盖率换成了性能。

5. 精度测试

### 5.1 原配置与 v11 对比（EvalScope 默认协议）

**方法**：沿用 `profiles/qwen36_35b_a3b_eval_20261007/REPORT.md` 的流程。

- 评测框架与数据：EvalScope 1.12，使用同一份本地数据集。
- 评分：rule 评分，0-shot；batch 32，seed 42，不使用缓存。
- 采样：Instruct 模型，不开 thinking，采样取 generation_config（T=0.7、top_p=0.8、top_k=20），`max_tokens` 为 16384。
- 服务端：`--max-model-len 32768`。
- 脚本：`tools/ppu/qwen3_vl_moe/eval_qwen3_vl.sh`。

| 数据集 | 原配置 | v11 | 结果目录 |
|---|---:|---:|---|
| GPQA Diamond（198 题） | 54.55% | 57.58% | `profiles/q_eval_{native,v11}_gpqa_20261020` |
| ERQA（400 题） | 31.25% | 31.25% | `profiles/q_eval_{native,v11}_erqa_20261020` |

- 加上官方采样参数（presence_penalty 1.5，`max_tokens` 32768）后：v11 是 57.07%（每题 3 次，共 594 样本），原配置是 59.60%（只跑了 1 次，198 样本）。差距在统计误差范围内（594 样本的标准误约 2%）。目录：`profiles/q_gpqa2_{v11,native}_20261020`。
- 数值验证：HF 与 vLLM 的 logprob 平均差 0.016，没有发现数值问题。

### 5.2 GPQA 与官方 70.4 的差距

官方数据来源是 Qwen3-VL 技术报告（arXiv 2511.21631）Table 4，Qwen3-VL-30B-A3B-Instruct 的 GPQA 为 70.4。报告中的评测设置是：temperature 0.7、top-p 0.8、top-k 20、presence penalty 1.5、最大输出 32768 token。这套参数和我们 5.1 的第二组完全一样，所以差距不来自参数。

为了定位原因，我在 v11 上做了一组 prompt 对照。

- 脚本：`profiles/q_prompt_eval_20261020/gpqa_prompt.py`。
- 设置：198 题 × 3 次，共 594 样本；采样用官方参数；选项顺序按固定种子打乱，所有方案使用同一份打乱结果。
- 打分：`rescore.py`，答案抽取规则放宽，兼容 `` `answer`: "A" `` 这类写法。

| Prompt 方案 | 准确率 | 3 次分别 | 无答案 | 截断 | 输出中位数（token） |
|---|---:|---|---:|---:|---:|
| boxed："Please reason step by step, and put your final answer (the option letter) within \boxed{}." | **71.55%** | 68.2 / 73.7 / 72.7 | 4 | 5 | 3847 |
| Qwen 推荐的 JSON `answer` 字段 | 68.18% | 67.7 / 67.7 / 69.2 | 7 | 5 | 2697 |
| EvalScope 默认（"ANSWER: [LETTER]"，5.1 用的模板） | 60.44% | 62.6 / 58.1 / 60.6 | 2 | 2 | 496 |
| EvalScope 默认 + system prompt | 58.59% | 57.6 / 57.1 / 61.1 | 2 | 2 | 504 |
| simple-evals 风格（"Answer: $LETTER"） | 57.41% | 56.6 / 56.6 / 59.1 | 0 | 0 | 496 |
| EvalScope 默认 + 贪心解码 | 55.89% | 54.0 / 54.5 / 59.1 | 29 | 34 | 498 |

**结论**：

- 用 "ANSWER: X" 这类末行格式的模板时，模型的推理会被压缩到约 500 token，分数在 57~60。
- 用 boxed 或 JSON 写法时，模型会充分推理，输出 2700~3800 token，分数在 68~72。
- 贪心解码容易陷入重复循环，34 条被截断，分数反而更低。
- 因此 57 分和 70 分的差距来自 prompt 协议，与适配无关。之后对外报 GPQA，建议统一用 boxed prompt。

**局限**：boxed prompt 只在 v11 上测了，原配置没有测。原配置在 40k 上下文下跑得很慢，64 并发时总共只有约 50 tok/s，一组就要好几个小时，所以中途停掉了。5.1 已经确认同一协议下 v11 和原配置持平，可以推断原配置用 boxed prompt 也在 70 左右，但没有实测。

### 5.3 已知问题：ERQA 输出以一串 `!` 开头

ERQA 中有少量输出以一串 `!` 开头（token id 0），后面是乱码。

| 配置 | 出现条数（/400） |
|---|---:|
| 原配置 | 17 |
| v11 | 6 |
| v11 去掉 STABLE | 0 |

这个问题原配置本身就有，不是 v11 引入的。单独调用 MoE kernel 测试时，M=1500/4100/8192 以及偏斜路由下都没有出现 NaN，根因尚未定位。GPQA 的所有方案中没有出现这种输出。
