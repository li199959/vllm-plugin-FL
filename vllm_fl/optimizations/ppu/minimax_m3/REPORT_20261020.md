1. 配置与命令
-------------

**最终配置**：`vllm_fl/optimizations/ppu/minimax_m3/`，通过 PYTHONPATH 加载本工作区，系统安装的插件未改动。

```bash
cd /mnt/cpfs/xiangbin/codex/minimax-m3-coverage-80
export PYTHONPATH=$PWD
export VLLM_FL_TOPK_DISPATCH=1
export VLLM_FL_MOE=hybrid                # decode MoE: DeepGEMM（关闭 GEMV）；prefill MoE: 调过 tile 的 Gems
export VLLM_FL_M3_DENSE=hybrid           # decode 线性层: split-K Triton / Gems
export VLLM_FL_M3_GEMMA_NORM=flaggems
export VLLM_FL_M3_FUSED_IMPL=triton
export VLLM_FL_FLAGOS_BLACKLIST=index_copy_,index,linear,addmm,mm,empty.memory_format
vllm serve /mnt/cpfs/xiangbin/MiniMax-M3/ --host 0.0.0.0 --port 8100 \
  --tensor-parallel-size 16 --gpu-memory-utilization 0.85 --max-model-len 32768 \
  --block-size 128 --no-enable-prefix-caching --trust-remote-code
```

- 性能测试服务由 `profiles/inlen_debug_20261012/start_variant.sh` 启动，开关同上。区别在于：`index` 不在黑名单里，而是由 hybrid 默认设为原生；另外加了 `FLAGGEMS_DB_URL=sqlite:///:memory:`。
- 原配置（base）：`VLLM_FL_MOE=deepgemm`，黑名单 `index_copy_,index,linear,addmm,mm,empty.memory_format`，不设 hybrid 开关，其余参数相同。

**压测命令**（三个场景只有 `--random-input-len` 不同）：

```bash
vllm bench serve --backend vllm --model /mnt/cpfs/xiangbin/MiniMax-M3/ \
  --endpoint /v1/completions --host localhost --port 8100 \
  --dataset-name random --random-input-len {1024|4096|16384} --random-output-len 1024 \
  --ignore-eos --max-concurrency 64 --num-prompts 256
```

- 共 256 个请求，并发 64，request_rate=inf，seed=0，random_range_ratio=0。
- 正式压测前，先用相同的输入长度跑 64 个请求预热。下面的日志都是预热之后、编译和 graph 都已完成时的稳态轮。
- 服务端设了 `--no-enable-prefix-caching`，结果不受缓存命中影响。

4. 算子覆盖率
-------------

统计口径为 vllm-gpu-coverage skill：GPU 关联的 ATen 加独立 GPU kernel，分子是 Gems 实现和有证据的 Triton kernel。case 为 4k/1k，64 并发，128 请求。先跑两轮预热，再抓一轮 profile。目录：`profiles/minimax_m3_final_cov_20261014/gpu_coverage`。

| 范围 | 已覆盖/总数 | 比例 |
|---|---:|---:|
| GPU 关联 ATen | 17/19 | 89.47% |
| 独立 GPU kernel | 35/43 | 81.40% |
| **合计** | **52/62** | **83.87%** |

- verification 通过。16 个 rank 都采到了 graph replay，79 个原始 kernel 符号都已归类。
- 未覆盖的 ATen：`index`。它改回原生，是因为 Gems index 会让每个 PIECEWISE graph 多占约 44 MiB，KV cache 因此少约 1 GiB。另一项是 `mm`：prefill 的大矩阵乘在 Gems 上慢 15–40%。
- 未覆盖的 kernel：DeepGEMM grouped GEMM（2 个）、pccl 通信（4 个）、computeBlockInfo、flashinfer 采样。

5. 精度测试（GPQA Diamond）
---------------------------

**方法**：沿用 `profiles/qwen36_35b_a3b_eval_20261007/REPORT.md` 的流程。

- 评测框架与数据：EvalScope 1.12；本地数据集 `AI-ModelScope/gpqa_diamond`，sha256 前缀 514eb956。
- 评分：198 题全量，0-shot，rule 评分；答案取 `</mm:think>` 之后的部分。
- 运行参数：batch 32，seed 42，不使用缓存。
- 采样：M3 是思考模型，采样参数取其 generation_config，T=1.0、top_p=0.95；开启 `thinking_mode=enabled`，`max_tokens=30000`。
- 服务：TP16，使用上面的最终配置，`--max-model-len 32768`。
- 脚本：`tools/ppu/minimax_m3/eval_gpqa_m3.sh`。

**结果**：

| 数据集 | 正确/总数 | 准确率 | 达到 30000 token 上限 | 输出出现一串 `!`（异常） |
|---|---:|---:|---:|---:|
| GPQA Diamond | 171/198 | **86.36%** | 14（无有效答案的计为错） | 0 |

报告文件：`profiles/m3_eval_gpqa_20261020/gpqa/reports/MiniMax-M3-FL/gpqa_diamond.json`。逐题预测和评分在同目录的 `predictions/`、`reviews/` 下。

**运行过程**：

1. 第一次运行到第 153 题时，一个 worker 卡在 `sample_tokens`。5 分钟后 RPC 超时（`TimeoutError: RPC call to sample_tokens timed out`），引擎退出，剩下的 45 题全部返回 500。
2. 处理：用 SIGKILL 清掉残留 worker，确认 GPU 状态正常；用同一配置重启服务（`profiles/m3_eval_gpqa_r2_20261020`），再用 `USE_CACHE=` 让 EvalScope 复用已保存的 153 题回答，只生成剩下的 45 题。
3. 两段使用同一配置、同一 seed、同一采样参数。已保存的 153 题全部正常结束，没有异常输出。
4. 卡死原因尚未定位。在长时间跑思考负载时，M3 可能存在稳定性问题。

**局限**：没有在同样条件下测原配置的 GPQA，所以这个分数不能说明优化前后精度有没有变化。如需对照，用原配置以相同方法再测一轮即可，约 1 小时。
